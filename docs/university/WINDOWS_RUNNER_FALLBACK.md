# Резервный runner на Windows с Docker Desktop

План применяется, если университетский runner недоступен или университет не может предоставить разрешённый исполнитель для сборки и запуска образа. Регистрация, запуск runner и изменение способа исполнения требуют подтверждения владельца компьютера. Этот план пока не выполнялся.

1. Уточнить у университета, разрешены ли собственные Project runners, доступен ли runner для этого проекта и какая версия GitLab Runner совместима с сервером. Проверить, что Docker Desktop работает в режиме Linux containers, а его контейнеры достигают `vcs.uni-dubna.ru` через HTTPS с действительной проверкой сертификата. Выбрать конкретный официальный тег `gitlab/gitlab-runner` после сверки версий. [Совместимость регистрации](https://docs.gitlab.com/runner/register/)
2. После подтверждения владельца создать **Project runner** только для EFIR Studio. Назначить тег `efir-windows-docker` и ограничить runner доверенными защищёнными ветками и тегами проекта. Для этого сценария задаются теги в job, чтобы локальный runner принимал только предназначенные ему задания.
3. Использовать Docker Desktop для запуска контейнера runner с Docker executor. Хранить `config.toml` и данные регистрации в именованном Docker volume вне репозитория. Зарегистрировать runner интерактивно, вводя выданный GitLab runner authentication token в локальный запрос. Docker socket требуется управляющему контейнеру runner для создания job-контейнеров и даёт ему контроль над Linux Docker engine. Job-контейнерам сам socket не передаётся. [Runner в Docker](https://docs.gitlab.com/runner/install/docker/)
4. Изменить `default.tags` на `[efir-windows-docker]` только если весь pipeline переносится на Windows. Если учебный runner успешно выполняет тесты, его теги остаются по умолчанию, а отличающийся тег добавляется только в шаблон `.docker` для `package` и защищённой публикации. Согласовать отдельный способ сборки и E2E в Docker, допустимый для этого runner. Например, для выделенного Docker executor GitLab поддерживает разрешение привилегий только конкретному rootless-сервису Docker-in-Docker. Конфигурация job должна указывать соответствующий образ и соединение. [Ограниченный Docker-in-Docker](https://docs.gitlab.com/runner/executors/docker/#use-rootless-docker-in-docker-with-restricted-privileged-mode)
5. Проверить **online** в GitLab, затем запустить pipeline. Сверить runner и executor в журнале `lint`, результат реального E2E в `container` и порог 95% в `coverage`. Загрузить JUnit, Cobertura и HTML. Ноутбук и Docker Desktop должны оставаться запущенными до завершения заданий. После приёмки остановить выделенный контейнер runner, если он больше не нужен.
